## 1. What was implemented

1. **`scripts/rf_bench.py`** — synthetic SDPA benchmark, decoupled from mahjong data:
   - reads a YAML benchmark config, hashes it, validates every field (fail closed);
   - device `auto|cuda|cpu`; CUDA requires BF16 autocast per the card;
   - per shape `(B,L,d)` and per phase `forward` / `train` (fwd+bwd) / `step` (fwd+bwd+AdamW):
     warmup then measured loop, `torch.cuda.synchronize()` per step, records ms/step, tokens/s,
     p50/p95, `max_memory_allocated` / `max_memory_reserved`, start allocation;
   - `reset_peak_memory_stats` before each measured phase; AdamW state is allocated in warmup so
     the `step` phase measures steady state;
   - **OOM/ERROR record-and-continue**: the failing phase keeps `ms_per_step: null`,
     `tokens_per_sec: null`, the exception text and the peak memory seen so far; the next shape still
     runs. Status is `BLOCKED` (exit 2) if no shape passes the required `train` phase;
   - records GPU UUID (normalized to `GPU-…`), total/free VRAM before the run, driver, sm_120,
     BF16 flags, cuDNN, Python/torch/numpy/PyYAML versions, WSL flag, `/dev/shm`, start method,
     config hash, git SHA and a read-only disk budget (zips, extracted, checkpoints, free space);
   - safety fields assert no downloads/installs/background jobs/GPU setting changes; only `--out` is written.
2. **`configs/riichiformer/benchmark.yaml`** — the four candidate shapes from the card
   `(8,512,256)/(4,1024,384)/(2,2048,384)/(1,4096,384)`, 2-layer 4-head causal SDPA block,
   BF16, warmup 10 / measure 30, AdamW, disk scan paths. It is a benchmark template, not a model config.
3. **`docs/riichiformer/GPU_ENV.md`** — measured device facts, result table, storage budget,
   WSL dataloader rules, dependency pins and the shared-GPU caveat.
4. **`tests/rf_test_bench.py`** — 16 tests: config validation (heads divisibility, required train phase,
   dtype/phase/shape errors), CPU execution of all three phases, p50/p95, **simulated OOM records
   `null` and continues to the next shape**, blocked-status logic, config byte hash, read-only disk
   scan, CLI CPU smoke artefact, bad-config exit 1, JSON serialisability of environment (regression for
   `_CUuuid`), GPU UUID normalisation, and a tiny real GPU BF16 smoke (`2×32×64`, skipped without CUDA).

## 5. Risks / limitations

- **Shared GPU**: numbers are valid but not exclusive-GPU performance; PR-17 must re-run under the
  train lock on an idle GPU. The torch/nvidia-smi free-memory disagreement is recorded, not “fixed”.
- **Synthetic model**: 2 layers, no embeddings/heads/KV cache; do not extrapolate peak VRAM or
  tokens/s to MVP-S/Main-H/Flat-F. GC step does not include per-game batching.
- **Extracted data is smaller than the documented expectation** (11.44 GiB vs “40–60 GB”); this is
  exactly why PR-02 must audit local files instead of trusting docs. No data was modified.
- **New dev dependency**: `PyYAML==6.0.3` installed into `.venv` for `rf_*` YAML configs; torch still
  `2.11.0+cu128`. The benchmark itself never installs anything.
- p95 is computed from 30 steps; treat it as a coarse latency indicator, not a tail guarantee.
