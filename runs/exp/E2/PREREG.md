## 1. Arm definition (E2, the control arm)

`[model] use_event_branch = false` is written **explicitly** in `configs/exp_e2.toml` /
`runs/exp/E2/train.toml` / `runs/exp/E2/eval.toml`. Consequences, asserted by
`runs/exp/E2/measure_params.py`:

- `Brain.event_branch is None` → the event branch is **not instantiated** (patch 0007,
  `mortal/model.py:243-250`); `event_branch.*` tensors in `state_dict()` = 0;
- `Brain.forward` is bit-for-bit the pre-0007 CNN path; the `events=` argument is accepted
  (patch 0010) but inert. The dataset/arena still build and feed the token stream, so E2 and
  E3a see the **identical data pipeline** — only the branch's consumption of it differs;
- training never raises the "branch enabled but `events` is None" guard, and evaluation of
  the E2 checkpoint resolves `use_event_branch=false` from the checkpoint's own config
  (`brain_from_config`) — E2 cannot silently become anything else.

Architecture: `ResNet(conv_channels=202, num_blocks=40)`, version 4, no event branch.

## 2. Parameter counts (measured `sum(p.numel())`, not parsed from logs)

Source: `runs/exp/E2/measure_params.py --out runs/exp/E2/params.json` (env `source
scripts/activate_env.sh`, patch 0007 applied). The E3a numbers were re-derived by
instantiating `Brain(..., use_event_branch=True)` and agree with todo 19a's
`runs/exp/E3a/PREREG.md` §3 / `selfcheck.json` exactly.

| object | numel |
|---|---|
| baseline CNN (c=192, b=40) | **10,787,456** |
| E3a added by the event branch | **1,031,296** (9.56 % of the baseline) |
| **E3a total** | **11,818,752** |
| **E2 chosen: CNN (c=202, b=40)** | **11,775,996** |
| E2 added by an event branch | **0** |
| **E2 total − E3a total** | **−42,756 (−0.3618 %)** |
| added-parameter difference (E3a added − E2 added) | **1,031,296** |

`conv_channels = 202` was selected by scanning c ∈ [190, 225] (`params.json → scan`): the
analytic estimate in the plan (≈201, not 210) is confirmed; 202 minimises `|total_E2 −
total_E3a|` (0.3618 % ≤ 5 %). Note 197–208 all satisfy the 5 % band; 202 is the closest.

Analytic consistency (branch-absent proof): for E2 `sum(p.numel())` equals the closed-form
pure-CNN count `analytic_cnn(202, 1012) = 11,775,996` exactly, and the same formula reproduces
the c=192 baseline `10,787,456`. The c=192 measured value equals `10,787,456` in
`runs/exp/E3a/selfcheck.json → numel.baseline_cnn_total`.

Caveat recorded honestly: total capacity is matched, *distribution* is not — E3a's last
1.03 M parameters sit in a separate attention branch, E2 spreads ≈1.03 M across wider
convolution channels. The verdict (todo 22) compares the two *parameter-matched*
architectures, not identical compute: E3a's measured step cost was 220 ms vs 133 ms for the
c=192 CNN (≈1.65×), so E2 is expected to be *slower per step* than the c=192 baseline and
maybe comparable to E3a. This is a stated limitation of the "parameter match" criterion
(the plan's documented fallback is "same FLOPs"; it was not needed).

## 3. Training protocol (declared BEFORE launch)

- **Step budget: 20,000 optimizer steps** — the exact budget E3a declared (`runs/exp/E3a/
  PREREG.md` §5); batch 1024, `opt_step_every=1` ⇒ 20.48 M samples, **from scratch** (no
  resume; same rationale as E3a: E2's channels differ from every existing checkpoint and a
  warm-start for one arm only would break the comparison).
- Config `runs/exp/E2/train.toml` / `configs/exp_e2.toml`, generated by
  `runs/exp/E2/make_configs.py` from `configs/config.toml.bak-19` (pre-0007 base) with
  exactly the changes the E3a generator made, plus the arm-specific ones:
  `[resnet].conv_channels=202`, `[model].use_event_branch=false`, all paths under
  `runs/exp/E2/`.

**Conditions matched to E3a bit-for-bit** (verified by tomllib diff against
`runs/exp/E3a/train.toml`): `batch_size=1024`, `opt_step_every=1`, `save_every=2000`,
`test_every=100000`, `submit_every=400`, `enable_amp=true`, `enable_cudnn_benchmark=true`,
**`enable_compile=false`**, `num_workers=3`, `file_batch_size=5`, `reserve_ratio=0.0`,
`num_epochs=1`, no augmentation, identical dataset globs (train 2009–2022, holdout 2023),
`val_batches=20`, `file_index=checkpoints/file_index.pth` (read-only), `freeze_bn.mortal=false`,
`optim` (eps/betas/weight_decay/max_grad_norm) and `optim.scheduler` (peak=final=1e-4,
warm_up_steps=0, max_steps=0) unchanged, `gamma=1`, `pts=[6,4,2,0]`, `cql`/`aux` unchanged.

**Unavoidable differences (all documented, none confound the architecture contrast):**

1. `resnet.conv_channels` 192→202 — this *is* the intervention that matches E3a's parameter
   total; the network is wider instead of branched.
2. Random initialisation and dataset file order are **unseeded** in the framework
   (`train.py`/`dataloader.py` contain no `manual_seed`; `dataloader.py:60` uses
   `random.shuffle`). Both arms start from scratch with different draws; this adds
   run-to-run variance to the comparison, which is exactly what the pre-registered pool-B
   verdict and its noise floor handle.
3. Paths (checkpoints/TB/game logs) point to `runs/exp/E2/` instead of `runs/exp/E3a/`.
4. E3a's resume (12,000 → 20,000 steps) may share the GPU with E2's *evaluation* only after
   E2's training has finished; training is serialized one `train.py` at a time (hard rule).

**Safety**: the four live paths (`state_file`, `best_state_file`, `tensorboard_dir`,
`test_play.log_dir`) plus `train_play.log_dir` are asserted non-live by the generator at
generation time and re-read before launch; the mtimes of `checkpoints/mortal.pth` /
`checkpoints/best.pth` are checked before/after training. The repo config
(`configs/config.toml`) is never used to train.

Training log: `runs/exp/E2/train.log`; checkpoints `runs/exp/E2/state.pth` every 2,000 steps;
TB scalars `runs/exp/E2/tb`.

## 4. Arm evaluation protocol (pool A, declared BEFORE launch)

- 12,000 games = 3,000 sets, `seed_key = 0x5dfaa4cef265cd7`, **`seed_start = 10000`**
  (pool A). **Pool B `50000` is reserved for todo 22 and must not be consumed here.**
- challenger = `runs/exp/E2/state.pth` (the arm); champion =
  `checkpoints/mortal.pth.at-148800` (same champion as every other pool-A arm).
- own `log_dir` = `runs/exp/E2/games/` (no other arm shares it; `runs/1v3/` is never written).
- Config: `runs/exp/E2/eval.toml`; launch from `vendor/mortal/mortal` with
  `MORTAL_CFG=<abs path>/runs/exp/E2/eval.toml python3 one_vs_three.py`
  (not `scripts/run_eval.sh`, which hardcodes its shell log to `runs/1v3/`).
- Report: `scripts/eval_report.py --games-dir runs/exp/E2/games --seed-key
  0x5dfaa4cef265cd7 --seed-range 10000-13000 --checkpoint state.pth --source-dir
  runs/exp/E2 --out runs/exp/E2/report.csv`.
- **Resolution context**: at 12 k games the minimum detectable difference at 80 % power is
  ≈ **0.0239 avg_rank / 1.86 pt** (`runs/variance/README.md`; σ_set = 0.4678 / 36.37).
  Effects below that are *not* evidence of no effect.
- **Interpretation**: pool A feeds the five-arm ranking only. The architecture verdict
  (todo 22) is E3a vs E2 with primary criterion "Δpt 95 % CI lower bound > 0" measured
  **once** on pool B. A null/negative pool-A outcome here is a valid result.
- Frozen-corpus invariant: `runs/1v3/*.json.gz` stays at exactly 2,004 files.

## 6. Addendum — interruption and resume (2026-09-18)

The first training process (pid 5746, started 2026-09-18 02:02:00) was killed by a **host
reboot at ~02:40**, mid-way between the step-4,000 save (02:28:58, holdout_loss 4.236074)
and the step-6,000 boundary. The last completed save is `runs/exp/E2/state.pth` at
**step 4,000**. The run was resumed at **20:34:07** from that checkpoint with the *same*
`runs/exp/E2/train.toml`: optimizer / scheduler / scaler / best_perf state all come from the
checkpoint, and the **declared 20,000-step budget is unchanged** (16,000 steps to go).

This is a resume of the arm's *own* interrupted run, not a warm start from a foreign or
pretrained checkpoint: §3's from-scratch rule forbids starting either arm from an existing
trained model (which would break the E3a-vs-E2 comparison), and no such checkpoint enters
this training. The resume checkpoint was verified before launch: `steps=4000`,
`config.resnet.conv_channels=202`, `config.model.use_event_branch=False`,
optimizer/scheduler/scaler present, 0 `event_branch.*` keys.

One honest caveat, recorded here because it is a property of the interruption rather than of
the protocol: `train.py` shuffles the file list and slices it across DataLoader workers per
process, so the **sample order after resume does not continue the pre-kill order** (the same
number of steps is run, over a fresh random pass of the corpus). This is identical to the
resume caveat in `runs/exp/E3a/PREREG.md` §8 — both arms carry it, so the comparison stays
symmetric. The step counts remain comparable element-wise: 4,000 + 16,000 = 20,000 optimizer
steps at batch 1024.

The resumed segment is logged to `runs/exp/E2/train.log.resume` (the original `train.log` is
kept intact); both together are the arm's training log. The resumed process prints the same
`mortal params: 11,775,996` as the pre-reboot process.
